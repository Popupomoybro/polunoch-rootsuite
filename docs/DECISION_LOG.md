# DECISION_LOG.md — принятые решения и причины

> Каждое решение: контекст → выбор → почему → альтернативы → последствия.

## D-01. Откат на рабочую базу 22.11 вместо дальнейшего ремонта стекла (23.11 вечер)
* **Контекст:** стеклянная сборка (master) крашила на старте; пользователь испытал серию крашей; доверие к итерациям потеряно.
* **Решение:** собрать и выдать как рабочую версию коммит `531ba00` (последний перед стеклянным редизайном), зафиксировать тегом.
* **Почему:** правило «стабильность важнее скорости» (§11); база доказана прогоном 22.11 (логи сервера: полные модули, VERDICT, RUN done).
* **Альтернатива:** продолжить чинить стекло на мастере — отвергнута: три круга чининга не дали запуска.
* **Последствия:** функциональность 49 модулей/лога/цепочки сохранена; UI — старый (не стекло); тег `stable-2211-working` + бэкап как страховка.

## D-02. KCE-свип имён kernelcache убран, а не починен (24.11)
* **Контекст:** на устройстве все 26 кандидатов путей дали ENOENT через sandbox-escape; opendir директории — EPERM.
* **Решение:** вырезать свип; в логе — одна строка про posture escape'а.
* **Почему:** на 26.2b1 ядро не читается файлом этим escape'ом (sealed volume); образ уже есть локально, UUID-сматченный. Свип жёг ~26 строк лога и секунды на каждый запуск.
* **Альтернатива:** расширить свип — отвергнута: оснований нет (все семейства имён покрыты).

## D-03. Модули-ярлыки unit3/unit6 direct вместо изменения естественной последовательности (24.11)
* **Контекст:** resumable-модуль тратит 3 запуска на юниты 0–2, прежде чем дойти до формы паники (unit3).
* **Решение:** новый вход `ModIsurfUAFAt(unit)` — прямой старт с выбранного юнита, без KCE-стадии.
* **Почему:** паницу надо ловить сериями; экономия запусков = скорость набора статистики. Естественная последовательность сохранена (phase2 как есть).
* **Последствия:** unit3 → паница за один запуск (подтверждено); unit6 → 36 раундов чисто (отрицательный результат зафиксирован).

## D-04. MRR в build.sh не переводим на ARC (23.11, подтверждено 24.11)
* **Контекст:** сборка идёт без `-fobjc-arc`; найденные autoreleased-в-static присваивания исправлены через `alloc/init` (корректно в обеих моделях).
* **Решение:** флаг не менять; новый код писать совместимо с обеими моделями.
* **Почему:** рабочая версия собрана в MRR и работает; перевод на ARC — полный регресс 49 модулей ради гипотетической безопасности памяти; найденныеspecific-дефекты уже исправлены точечно.
* **Последствия:** утечки в коде возможны (как и были), но не corruption; зафиксировано как долг.

## D-05. Лог храним строкой, не UITextView (23.11)
* **Контекст:** .ips 16:33: `initWithString: → NSRLEArray → _xzm_xzone_malloc_freelist brk 1` — TextKit на каждую строку лога в off-screen TextView.
* **Решение:** хранилище — `NSMutableString`-кольцо 256КБ + `AveLogText()`; TextView только когда окно реально открыто.
* **Почему:** устранена цепочка из .ips; стоимость — отсутствие «живого» авто-скролла в фоне (не нужен).
* **Последствие:** устранён класс дефектов; признано, что это была жертва, а не виновник стартового краша (виновник не в логе — см. PANIC_ANALYSIS).

## D-06. POST-миррор с капом, а без ограничений (23.11)
* **Контекст:** теория «шторм data-task» как причины memory-kill.
* **Решение:** ephemeral-сессия, max 2/host, 2с, кап pending 64, отставание → отбрасывание.
* **Статус:** теория не подтвердилась как причина крашей (рабочая 22.11 постила тысячи строк и не умирала), но ограничение оставлено как корректное поведение.

## D-07. Дизайн: возврат стекла поэтапно на базу (24.11)
* **Контекст:** стекло на мастере крашит запуск; причина в стеклянной оболочке, не в базе.
* **Решение:** стекло возвращается поверх `hunt-unit6` малыми шагами: (1) UITabBar-каркас без материалов → (2) слоистые материалы карточек → (3) UIGlassEffect-панели; на каждом шаге — сборка + проверка запуска (T1).
* **Почему:** бинарный поиск по компонентам дешевле слепого чининга; база остаётся рабочей на каждом шаге.
* **Альтернатива:** чинить мастер напрямую — отвергнута (три круга без результата).

## D-08. Исследование: фокус на диагностику, не на цепочку эксплуатации
* **Контекст:** правила проекта запрещают разрабатывать произвольную запись в ядро/подмену ucred ради UID 0.
* **Решение:** все направления формулируются как «доказать или опровергнуть» с канареечными/лог-микстами; root только через `RootProbe`.
* **Последствия:** честный статус ROOTSTATE NO; deliverable'ы — доказательная база, а не эксплойт.

## D-09. Паникy не считать доказательством UAF
* **Контекст:** миссия явно требует разделять VERIFIED / LIKELY / HYPOTHESIS / UNKNOWN.
* **Решение:** в `PANIC_ANALYSIS.md` паница объявлена VERIFIED-фактом (инструкция, путь, поле), а UAF — HYPOTHESIS с альтернативным объяснением (teardown-гонка, NULL-lock).
* **Последствия:** план проверки однозначен (канарейка в far — тогда UAF; 10× NULL — тогда закрывать).
